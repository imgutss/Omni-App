# guts — رله‌ی گوگل برای روزی که فقط گوگل باز است

`guts` یک تونل TCP کامل است که **درِ ورودش گوگل است** و **خروجی‌اش هر جایی که از گوگل دیده شود** — لازم نیست از ایران دیده شود.

```text
📱 گوشی ──TLS با SNI=www.google.com──► Google Edge ──► Apps Script (اکانت خودت)
        ──► Exit Node (VPS / رانر رایگان GitHub + cloudflared) ──► اینترنت
```

سه تکه دارد و **هیچ‌کدام پولی نیست**:

| تکه | چیست | هزینه |
|---|---|---|
| `apps_script/Code.gs` | «در»: یک Web App روی اکانت گوگل خودت که بدنه‌ی درخواست را بی‌تغییر به خروجی پاس می‌دهد | ۰ |
| `cmd/exitnode` | «خروجی»: سوکت واقعی به اینترنت را نگه می‌دارد | ۰ روی رانر رایگان GitHub Actions |
| `cmd/gutsclient` | کلاینت: SOCKS5 محلی روی گوشی/کامپیوتر | ۰ |

> اصل ماجرا: **کلادفلر/هر سرویس دیگری در ایران بلاک باشد اهمیتی ندارد**، چون گوشی هرگز به آن وصل نمی‌شود؛ گوگل به آن وصل می‌شود.

## چه چیزی این را از mhrv بهتر می‌کند
1. **بدون VPS**: خروجی روی رانر رایگان GitHub Actions + تونل رایگان cloudflared بالا می‌آید (`deploy/guts-exit.yml`).
2. **بدون MITM و بدون CA**: تونل TCP واقعی است، پس تلگرام/بانک/بازی هم کار می‌کنند.
3. **در، احمق است**: Apps Script هیچ مقصدی را fetch نمی‌کند؛ فقط بدنه را پاس می‌دهد. یعنی هیچ صفحه‌ای در گوگل باز نمی‌شود و مشکل «Turnstile» و «۵۰۴ Relay» از ریشه نمی‌آید.
4. **مسیر کوتاه‌تر**: یک VLESS/VMess می‌تواند داخل همین تونل بنشیند (mux) تا سهمیه و تأخیر کم شود.

## راه‌اندازی (۱۵ دقیقه)

نسخه‌ی کامل و کلیک‌به‌کلیک همین راه‌اندازی، با جدول خطاها: [SETUP.fa.md](SETUP.fa.md).

### ۱) خروجی
فایل `deploy/guts-exit.yml` را در ریپوی خودت زیر `.github/workflows/` بگذار، بعد:
Actions → guts exit → Run workflow → `key` = یک رمز طولانی → اجرا.
در پایان مرحله‌ی «Start the exit node»، آدرسی مثل `https://xxxx.trycloudflare.com/g` چاپ می‌شود. تا ۶ ساعت زنده است و هر بار می‌شود دوباره روشنش کرد.

اگر VPS داری، جای راحت‌تر:
```bash
go build -o guts-exit ./cmd/exitnode && ./guts-exit -addr :8080 -key "رمز-طولانی"
```

### ۲) در (Apps Script)
`apps_script/Code.gs` را در `script.google.com` بگذار، `AUTH_KEY` و `EXIT_URL` را پر کن،
Deploy → New deployment → **Web app** → Execute as: **Me** / Who has access: **Anyone** → آدرس `/exec` را بردار.

### ۳) کلاینت
```bash
# با فورواردینگ به گوگل (همان چیزی که در نت ملی کار می‌کند)
gutsclient -door "https://script.google.com/macros/s/XXXX/exec" -key "رمز-طولانی" \
           -google-ip 216.239.38.120 -sni www.google.com -listen 127.0.0.1:1080

# یا مستقیم به خروجی (برای تست خانگی)
gutsclient -door "http://127.0.0.1:8080/g" -key "رمز-طولانی" -direct
```
بعد مرورگر/اپ را روی `socks5://127.0.0.1:1080` بگذار. `-check` سلامت کل مسیر را تست می‌کند.

## پیدا کردن آدرس بازِ گوگل (اسکنر)
شبکه‌ی محدود فقط بعضی از IPهای گوگل را باز می‌گذارد و بعضی از نام‌هایی را که در ClientHello می‌آید فیلتر می‌کند؛ هر دو هم خاصیت همان خط‌اند (ایرانسل با همراه اول فرق دارد) و هر روز عوض می‌شوند. پس اسکنر داخل خود کلاینت است و آدرس و نام را **با هم**، به‌صورت یک ماتریس می‌سنجد:

```bash
gutsclient -scan-matrix               # جدول کامل: هر (آدرس، نام)، دست‌دادن TLS، آیا درخواست fronted را قبول کرد
gutsclient -scan-matrix-json          # همان، JSON (همان چیزی که اپ اجرا می‌کند)
gutsclient -door ... -google-ip auto  # موقع وصل‌شدن مسابقه می‌دهد و اولین زوجِ کارآمد را برمی‌دارد
```

سه تصمیم اسکنر را روی خط واقعی راستگو می‌کند:

- **بودجه برای هر مرحله جداست**: وصل‌شدن TCP، دست‌دادن TLS و خواندن جواب fronted هر کدام کل `-timeout` را می‌گیرند. روی یک خط واقعی دست‌دادنِ تنها سه ثانیه طول می‌کشد؛ مهلتِ مشترک آن خطِ سالم را «مرده» گزارش می‌کرد.
- **آدرس × نام با هم، نه پشت سر هم**: نام‌های جایگزین (۲۸ نام، از جمله `gstatic` و `googleapis` و `gvt2` که اپ‌های واقعی رویشان زندگی می‌کنند) روی همه‌ی آدرس‌های زنده تست می‌شوند، نه این‌که اول یک آدرس مجبور باشد با `www.google.com` جواب بدهد — وقتی خودِ www همان نام فیلترشده است، به بقیه هرگز نمی‌رسیدی.
- **آدرس‌های کاندید از خودِ خط می‌آیند**: اول جواب‌های DNS همان اپراتور برای میزبان‌های گوگل (داخل اپ، ریزالور اندروید آن‌ها را می‌دهد و با `-edge-candidates` به کلاینت می‌رسند؛ روی دسکتاپ کلاینت خودش resolve می‌کند)، بعد pool‌ِ توکار.

خروجی واقعی از یک اجرا (شبکه‌ی آزاد):
```text
address          sni                              handshake fronted  note
108.177.98.113   g1.gstatic.com                   4 ms      yes      status 302
216.239.34.120   g3.gstatic.com                   4 ms      yes      status 302
108.177.98.102   drive.google.com                 4 ms      yes      status 302
142.250.185.78   www.google.com                   -         no       connect: i/o timeout
```
یعنی همان چیزی که کل طرح به آن تکیه دارد: با یک نام گوگلی در SNI و **Host=script.google.com** لبه‌ی گوگل درخواست را می‌پذیرد (۳۰۲)، نه ۴۲۱ — و این‌که کدام نام و کدام آدرس، جواب همان خط است نه یک ثابت جهانی.

## چند در و خروجی‌ها
```bash
gutsclient -door "https://script.google.com/macros/s/A/exec" \
           -door "https://script.google.com/macros/s/B/exec" \
           -google-ip auto -pick -key "..."      # هر دور را پینگ می‌کند، سریع‌ترین اول، و روی خطا می‌چرخد
```
با چند اکانت گوگل/چند Apps Script، سهمیه‌ی ۲۰هزاری تقسیم می‌شود و یک deployment خراب همه‌چیز را نمی‌خواباند.

## پروفایل قابل اسکن (QR)
```bash
gutsclient -door "https://.../exec" -key "..." -google-ip 216.239.38.120 -export
# guts://eyJkb29yIjpbImh0dHBzOi8vLi4uIl0sImtleSI6Ii4uLiJ9

```
این دقیقاً قالبی است که اپ اندروید برای QR/deep-link مصرف می‌کند.

## تست محلی (بدون گوگل)
```bash
./scripts/smoke.sh      # خروجی + در قلابی + کلاینت + دانلود ۲ مگابایت و مقایسه‌ی md5
go test ./...           # تست‌های واقعی: دانلود ۲MB، رفت‌وبرگشت، ۸ اتصال هم‌زمان، کلید اشتباه
```

## حساب و کتاب سهمیه
هر رفت‌وبرگشت کلاینت = **یک فراخوانی Apps Script**. با `-t` پویا: وقتی داده در جریان است ~۸ ثانیه،
در سکوت ~۲۰ ثانیه. یعنی یک نشست بی‌کار حدود ۱۸۰ فراخوانی در ساعت؛ سهمیه‌ی ۲۰٬۰۰۰ در روز
یعنی چندین ساعت استفاده‌ی متعارف. با `mux` داخل تونل، ده‌ها کانکشن در یک نشست جمع می‌شود و
این عدد خیلی کمتر می‌شود.

## محدودیت‌ها (صادقانه)
- **UDP ندارد** → تماس و بازی آنلاین نه؛ QUIC را باید بلاک کرد تا اپ‌ها به TCP برگردند.
- تأخیر هر chunk = یک دور گوگل؛ برای وب/چت خوب، برای ویدیوی HD نه.
- اگر خودِ گوگل هم بسته شود (قطعی کامل)، هیچ راه ابری نیست.
- ToS گوگل/کلادفلر: این سرویس‌ها برای پراکسی ساخته نشده‌اند؛ با چند اکانت و مصرف متعادل ریسک را کم کن.
- تونل رایگان cloudflared هر سشن آدرس تازه می‌دهد (بعضی وقت‌ها کلادفلر به IPهای گوگل چالش می‌دهد؛ خطای JSON در لاگ در همان لحظه دیده می‌شود).

## داخل اپ اندروید (قدم ۳-ب)
اپ همان باینری را اسپاون می‌کند که دسکتاپ اجرا می‌کند (`libguts.so` از `compile-guts.sh`)،
دقیقاً با همان قراردادی که MasterDNS/DNSTT دارند:

```text
profiles → GutsCoreManager → libguts.so -listen 127.0.0.1:18002 → Xray: socks outbound 127.0.0.1:18002
```

دو چیز را اپ اضافه می‌کند که دسکتاپ لازم ندارد:

- **`-fd-control-unix-socket @omni-guts-…`** — داخل VPN، مسیر پیش‌فرض گوشی خودِ تونل ماست؛
  پس اتصال کلاینت به IP گوگل بی‌محافظ به تونل برمی‌گردد و حلقه می‌شود. بسته‌ی
  `guts/protect` هر سوکت را پیش از `connect` (در `net.Dialer.Control`) به
  `VpnService.protect` می‌دهد — همان پروتکل یک‌بایت + `SCM_RIGHTS` که موتورهای DNS هم
  استفاده می‌کنند. تست `protect_test.go` ثابت می‌کند سوکت **قبل از اتصال** تحویل داده می‌شود.
- **کلید در محیط، نه در command line** — کلاینت کلید را از `GUTS_KEY` می‌خواند، پس در
  `/proc/<pid>/cmdline` و در هیچ لاگی دیده نمی‌شود.

## پروفایل، QR و پینگ (قدم ۳-ج و ۳-د)
- **`guts://`** دقیقاً همان قالبی است که کلاینت با `-export` می‌دهد و با `-import` می‌خواند:
  بدنه = Base64URL(JSON) با کلیدهای `door` / `key` / `google_ip` / `sni` / `note`. یک تست، خروجی
  واقعی `gutsclient -export` را داخل اپ می‌خواند تا «QR پنل روی گوشی» از ریشه درست باشد.
- **ادیتور GUTS**: درها (هر خط یکی)، کلید، لبه‌ی گوگل (`auto`)، SNI؛ با همان اعتبارسنجی هسته
  (`GutsCore.normalize`) و پیام‌های مشخص برای هر خطا.
- **ایمپورت**: QR، کلیپ‌بورد، فایل، و لینک `guts://…` از تلگرام/مرورگر (UrlSchemeActivity).
- **پینگ پروفایل**: عدد فقط از مسیر واقعی می‌آید — `GutsDelayTester` یک کلاینت موقت روی همان
  پورت ۱۸۰۰۲ بالا می‌آورد و نمونه‌ها را از SOCKS خودش می‌گذراند؛ درِ خراب یا کلید غلط =
  «-۱ = بی‌پاسخ»، نه عدد سبز.

## mux: یک سشن برای همه‌ی اتصال‌ها (قدم ۴-ب)
بدون mux هر اتصال SOCKS یک سشن جدا بود: بیست تب باز = بیست `poll` هر بازه، و سهمیه‌ی
Apps Script همین‌جا تمام می‌شود. با mux گوشی **یک** سشن باز می‌کند و اتصال‌ها را به‌صورت
استریم داخلش می‌فرستد:

```text
push:  {op:"push", sid:"...", mu:true, s:7, d:"<base64>"}      ← هر استریم یک شناسه
poll:  {op:"poll", sid:"...", mu:true, n:131072, t:8000}
       ← بدنه = قاب‌ها: [s:4][len:4][data] و [s:4][0xFFFFFFFF] برای «این استریم تمام شد»
```

- بودجه در **یک** جا شمرده می‌شود: خروجی قاب‌ها هیچ‌وقت نصفه نمی‌شود؛ اگر جا نبود، بقیه
  برای poll بعدی می‌ماند (تست `TestFramesKeepTheirOrder` و `TestBytesAndTheEndTravelTogether`).
- هر استریم بافر و backpressure خودش را دارد؛ استریم تنبل پشت استریم پرمصرف گم نمی‌شود
  (ترتیب ثابت شناسه‌ها در هر poll).
- سشنی که فعلاً استریم زنده ندارد **بسته نمی‌شود**؛ برای اتصال بعدی می‌ماند.
- اگر خروجی سشن را گم کند (ری‌استارت/جاروب)، poll جواب `no session` می‌دهد: استریم‌های آن
  سشن با خطا تمام می‌شوند و اتصال بعدی سشن تازه می‌سازد — بی‌آنکه اپ چیزی را «سبز» ببیند.
- **کلاینت قدیمی/خروجی قدیمی**: خروجیِ قبل از mux در پاسخ `open` نشانه‌ی `info:"mux"` را
  ندارد. گوشی آن را می‌فهمد، mux را خاموش می‌کند و صادقانه یک سشن برای هر اتصال می‌سازد
  (`TestAnExitNodeWithoutMuxIsTold` و `TestALegacyExitNodeStillCarriesTraffic`).
- سوئیچ: `gutsclient -mux=false` مسیر قدیمی را برمی‌گرداند. پیش‌فرض روشن است.
- سود واقعی: تست `TestManyConnectionsShareOneSession` شش دانلود هم‌زمان ۲۵۶KiB را از یک
  سشن می‌گذراند و بعد بررسی می‌کند که خروجی **دقیقاً یک** سشن داشته باشد.

## لبه و نام: اسکنر داخل اپ (قدم ۶)
آدرسی که گوگل از آن جواب می‌دهد و نامی که در ClientHello لو می‌رود، هر دو **خاصیت شبکه‌اند**، نه
خاصیت رله. `gutsclient` هر دو را می‌سنجد:

```bash
gutsclient -scan-matrix-json -timeout=5s -scan-budget=80s   # هر (آدرس، نام) با هم: کدام زوج‌ها دروازه‌ی گوگل را دارند
gutsclient -probe -probe-budget=12s                         # آیا این شبکه اصلاً به گوگل می‌رسد (خروجی ۰/۳)
```

هیچ‌کدام یک تماس Apps Script نیست: فقط دست‌دادن TLS + یک درخواست fronted، یعنی **صفر مصرف
سهمیه**. داخل اپ، دکمه‌ی «Scan this network for a working edge» در ادیتور GUTS همین اسکن ماتریسی
را اجرا می‌کند — آدرس‌های کاندید را اول از ریزالور خودِ همان خط می‌گیرد و به کلاینت می‌دهد — و
`google_ip` و `sni` را از سریع‌ترین زوجِ جواب‌داده پر می‌کند؛ و اگر هیچ زوجی جواب ندهد، چیزی را
عوض نمی‌کند و همان را می‌گوید (`guts_scan_none`).
اسکن دو مرحله‌ایِ قبلی (اول آدرس با www، بعد نام‌ها روی آن) روی خطی که www سه ثانیه طول
می‌کشید شبکه‌ی سالم را مرده گزارش می‌کرد؛ `-scan-json` و `-scan-snis-json` برای سازگاری
مانده‌اند ولی سؤال درست همان ماتریس است.

## چند اکانت گوگل: تقسیم سهمیه (قدم ۷)
سهمیه‌ی Apps Script **به ازای هر اکانت** است، پس چند اکانت (چند Apps Script، چند `-door`) فقط وقتی
به هم اضافه می‌شوند که تماس‌ها تقسیم شوند؛ کلاینتی که همیشه از سریع‌ترین در استفاده کند، روزِ یک
اکانت را می‌سوزاند و بقیه بیکار می‌مانند.

```bash
GUTS_DOOR_BUDGET=18000 GUTS_QUOTA_STATE=/data/.../guts-quota.json gutsclient -door=... -door=...
```

- شمارش «تماس هر در، در هر روز» با فایل وضعیت (پاک‌شدن فایل = فراموشی همان روز، نه خطای تونل).
- ترتیب سلامت حفظ می‌شود و بعد از آن دری که **بیشترین سهمیه‌ی باقی‌مانده** را دارد انتخاب می‌شود؛
  پس تا وقتی همه تازه‌اند همان درِ سریع برنده است و بعد از آن تماس‌ها به اکانت‌های دیگر می‌روند.
- سهمیه تمام‌شده = خطای صریح `every door has spent its daily call budget`، نه یک تونلِ نیمه‌مرده.
- عدد را با حساب خودت تنظیم کن؛ برای حساب مصرف‌کننده‌ی معمولی Apps Script سقف روزانه حدود ۲۰٬۰۰۰
  تماس است، و mux (قدم ۴-ب) نرخ را از «یک تماس برای هر اتصال» به «یک تماس در هر بازه» می‌آورد —
  با `DefaultPollMs` هشت‌ثانیه‌ای، یعنی حدود ۱۰٬۸۰۰ تماس در روز برای یک گوشی که همیشه روشن است، و
  با `IdlePollMs` بیست‌ثانیه‌ای در حالت بی‌کار حدود ۴٬۳۰۰.

## VLESS داخل تونل: GUTS به‌عنوان حمل‌کننده (قدم ۸)
GUTS یک تونل TCP است، پس لازم نیست خودِ پروکسی باشد: می‌تواند **مرحله‌ی آخر یک زنجیره** باشد و
VLESS/VMess/Trojan/Shadowsocks رویش سوار شود.

```text
Xray → VLESS outbound (سرور خودت) ──dialerProxy──► GUTS socks 127.0.0.1:18002 ──► در Apps Script ──► خروجی ──► سرور VLESS
```

- `dialerProxy` هر hop را از hop بعدی رد می‌کند؛ پس GUTS فقط **آخرِ** زنجیره معنا دارد
  (`GutsDependency`)، چون آخرین hop را Xray خودش می‌diald.
- وسطِ زنجیره، داخل گروه سیاستی، یا کنار یک هسته‌ی بومی دیگر (Aether/MasterDNS/DNSTT) رد می‌شود؛
  پیام `guts_unsupported_combination` هم همین را می‌گوید.
- یک پروفایل GUTS آدرس ندارد (درش را دارد و روی لوپ‌بک گوش می‌دهد)، پس `hasServerAddress` مثل
  Aether با آن رفتار می‌کند تا زنجیره بی‌دلیل «پروفایل آدرس ندارد» ندهد.
- رول‌ست «فقط TCP» (قدم ۴-ا) روی همین حالت هم اعمال می‌شود، چون حمل‌کننده هنوز TCP است.

  هسته‌ی دیگر، دو GUTS، و پروفایل ناقص).
